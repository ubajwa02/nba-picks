# Skeptic review: prop split cards (cbb8041 pre-registration, fa4d0dc implementation)

**Verdict: ACCEPT as a research/watchlist tool. Not evidence of edge.** No blocking defects. The report's own caveats are accurate.

## Checks
1. **Lookahead and leakage: none found.** `history`, `defense_ranks` (d < date, same season), `key_teammates` (d < date), `mates_in_last_game` (the team's previous game) and the experiment's synthetic line (`gs[i-10:i]`) all use only games strictly before the event's ET date. The `allowed` totals are built over the whole file but filtered by date at query time. Validate events use explore-period history, which is legitimate.
2. **Pre-registration and holdout:** cbb8041 (04:58:30Z) precedes fa4d0dc (05:02:56Z), and the script reads only `box_2023`/`games_2023`, so the 2024-26 holdout is untouched. Caveats: (a) the registration's `"at": "2026-10-21T12:00:00Z"` is later than its own commit time, so it was hand-written and is wrong (LOW); (b) its `"commit"` field says `splitcard.py` already existed, uncommitted. Git proves only a 4.5-minute ordering and cannot rule out an earlier peek (LOW, unverifiable).
3. **Statistics: conclusions are robust to clustering (reproduced).** I re-ran the experiment (28 s) and recomputed the paired Brier-difference t with cluster-robust SEs. Validate vs season rate: naive -7.3, player-day clusters -6.3, player clusters (458) -4.8. Validate vs last-10: -7.8 / -6.4. Explore vs season: +3.9 (player-day) / +3.7 (player), so the **sign flip between explore and validate is real, not noise**. The gain over the season rate is not stable (it is plausibly a within-season effect: more data later in the season). Only "better than last-10" is solid. The flagged-hit-rate criterion is a construction artifact, as the report itself says. The pre-registered criterion was validate-only, so "criteria met" is technically correct but weak (MEDIUM, interpretive; already disclosed).
4. **Daily-run integration:**
   - It cannot change decisions: cards go to `state/split_cards_latest.json` only, inside a try/except. **Untested:** the failure path (an exception being swallowed and the run continuing) has no test (LOW).
   - Prices are DraftKings (`market == "prop" and book == "DraftKings"`), but a card carries **no `book` field**. `card_text` says "vs book", and `prob`, `implied` and `ev` sit beside it unlabelled. Nothing mislabels the price as FanDuel today, but any future rendering cannot tell which book's price the EV uses (MEDIUM; add `book` and `price_observed_at` to the card).
   - Individual cards carry no research label. Only the file-level `status` does, and the dashboard flattens the cards into `prop_split_cards` without it. No UI currently renders them, but an `ev` field on a card could later be shown as a pick (LOW-MEDIUM).
   - EV uses the raw `prob`, which the report shows is overconfident in the tails (0.82 predicted, 0.70 observed). So EV is biased upward exactly where it looks attractive (MEDIUM).
   - With missing data (no history, no props, a traded player), the code skips cleanly. `player_games.played` is NOT NULL, so live rows are not silently dropped.
5. **Claimed but not tested:** the teammate with/without logic is covered only by a loose `"with Mate" or "without Mate"` assertion; there is no point-in-time test for `key_teammates` or `mates_in_last_game`, no test for the rest-bucket split, and no test for the traded-player skip (LOW).

## Recommended (non-blocking)
Add `book` and `price_observed_at` plus a per-card `status: research` field. Suppress or label `ev` until it is calibrated against real lines (NBA-031). Add tests for the teammate and rest splits and for the swallowed-exception path. Fix the registration timestamp convention (use the commit time).
